| 2026-07-29 | dh_comms host-pinned alloc uses `hipHostMallocUncached` (MTYPE_UC) rather than fixing `0x4`→`0x40000000` (recommended path, not yet applied) | Uncached host memory bypasses device L2, avoiding instrumentation-induced L2 pollution/misses; also fixes the latent `0x4` (=WriteCombined) typo from commit `0c8a3635` | L2 cache-miss investigation (`.untracked/`) |

| 2026-09-08 | For code the application loads itself, index code objects instead of loading a second HSA executable | The private copy's `__constant__` segment is never initialised, so clones dispatched from it read `__device__`/`__constant__` globals as zero. The distinction is available statically at the call site (`getExecutablePath()`/`getSharedLibraries()` versus Triton cache and `--library-filter` includes); a runtime "already loaded?" test is impossible because `addFile` runs before the HSA intercept is registered | bf_hip-duplicate-code-object-load |
| 2026-09-08 | `-k` gates the clone swap at dispatch, not what `coCache` records | Gating the record made the filter select which *copy* a clone came from rather than *whether* one was used, and tied kernelDB coverage to the filter so a filtered run needed a sacrificial dispatched kernel to get DWARF. Dispatch-time gating matches the documented meaning and decouples the two | bf_hip-duplicate-code-object-load |
| 2026-09-08 | AC-9 amended to count a line emitted at the executable-load site, and its `[judgement]` marker dropped | The old check counted `Adding` log lines, which the fix renames — so a rename alone would have satisfied it. "Zero private loads on a pure-HIP workload" is anchored to the behaviour and is pinnable, unlike "materially fewer", which is what had required a human ruling | user-approved amendment, bf_hip-duplicate-code-object-load |
| 2026-09-08 | Re-record a suite baseline by building the base commit in a worktree, not by disabling the fix in place | The in-place reconstruction reverts only the half of the change guarded by one flag, and still runs the four suites the packet itself adds — which did not exist at the base commit, so the "before" and "after" tallies are not comparable. Building `74c6ed2` costs one configure and one parallel build and gives a real 6-suite baseline | bf_hip-duplicate-code-object-load (AC-4) |
| 2026-09-08 | Library-filter tests assert on `^(Adding\|Indexing) `, but only where the library is application-loaded | The filter runs before either line is printed, so both are equally good evidence a library survived it. The `libdynamic_*` checks stay on `Adding` alone: those come from a `--library-filter` include, are never mapped at startup, and widening them would only weaken them | bf_hip-duplicate-code-object-load (AC-4) |
| 2026-09-08 | The Python handler bridge ships as a **plugin** under `plugins/`, not as a core change | Linking `Python::Python` into `liblogDuration64.so` would make every consumer of the core library depend on libpython for a feature most do not use. The existing `LOGDUR_HANDLERS` → `dlopen` → `getMessageHandlers` ABI already supports this shape, and the IntelliKit spike proved it works out of tree in ~100 lines. Enforced mechanically by `bf_pyhandler-gil` AC-6, which fails if `ldd` shows libpython on the core library | owner decision, bf_pyhandler-gil |
| 2026-09-08 | Incoming seeds from other projects are committed unedited, then verified before becoming packets | Both IntelliKit seeds proved accurate, but verification still changed both packets: it found a second caller of `capture_subprocess_output` that constrains the fix, and it found that the GIL fix cannot be tested in isolation — which forced a scoping decision rather than a two-line bugfix. Taking a report at face value would have produced a packet whose own acceptance criteria were unreachable | session, seeds → packets |
| 2026-10-26 | The Triton staleness check keeps `exit 1`; a demotion to advisory was reverted the same day | The red run was doing two jobs — masking other CI failures on `main`, *and* serving as the owner's notification channel. Only the first is visible from inside the repo. GitHub emails on a failed run and sends nothing for exit 0; `::warning::` and step summaries notify no one, so "advisory" meant "silent". A crude notification that reaches someone beats a tidy one that does not. The permanent red goes away when the pin bump lands, not before — do not re-demote it | owner decision, asked and answered |
| 2026-10-26 | Validate a Triton/LLVM bump on a GPU node, not in CI | `build.yml` is build-and-install only, on `ubuntu-latest`, with no GPU and no test invocation — so the whole pipeline, including the ~4.5h toolchain image job, can only catch compile breakage. The dangerous class is semantic: `validateAMDGPUTarget`'s exact-triple match still compiles against new LLVM and silently skips every kernel. Bumping `TRITON_VERSION` is also what *triggers* the toolchain job, and since the image only pushes on success, a failure leaves `main` pinning the new version while `latest-rocm7.2` still holds the old one | session, Triton 3.8.0 planning |
| 2026-10-26 | Blanket removal of `amdgpu-no-*` from instrumented clones is preferred over a targeted list | A list of "the attributes dh_comms currently reads" goes stale silently the next time dh_comms reads something new — and silent staleness is the defect being fixed. Instrumented clones are already heavily perturbed, so the cost (extra SGPR setup, larger kernarg) is cheap there. Uninstrumented originals keep their attributes | assessment of PR #44 |
| 2026-10-26 | Use jq as a build prerequisite, but verify the LLVM tree's HEAD against the pin after the build rather than trusting Triton's script | Triton's `build-llvm-project.sh` fails silently on an empty or `null` pin and still exits 0. Patching Triton's script would be ours to maintain and would not cover users who bring a custom LLVM for their Triton; checking the outcome catches every cause (missing jq, `null`, refused fetch, stale mirror) without touching Triton. A caller's own `LLVM_COMMIT_HASH` is respected and verified against, not overridden | owner decision, Triton v3.8.0 bump |
| 2026-10-27 | Split the toolchain Dockerfile into `llvm` and `toolchain` stages and build `--target llvm` (cache-only) first | BuildKit exports cache only for a successful solve, so a failure after the ~2h LLVM build discarded it. The first v3.8.0 run lost exactly that to a transient NVIDIA CDN error | owner decision after CI failure |
| 2026-10-27 | Fix #43's item 1 before merging #44, so #43 closes with everything it raised addressed | #44 says `Fixes #43`, but #43's thread carried two further items; closing it on merge would have dropped the triple defect, which is certain to hit the next Triton bump on every GPU | owner decision |
| 2026-10-27 | `validateAMDGPUTarget` uses `llvm::Triple(TripleStr).isAMDGCN()`, not `M.getTargetTriple().isAMDGCN()` | `isAMDGCN()` tracks LLVM's `amdgcn`→`amdgpu` enum rename; parsing the string also keeps compatibility with LLVMs whose `getTargetTriple()` returns `std::string` | e6db747 |
| 2026-10-27 | Protect `main` (no force-push, no deletion, `enforce_admins` on); let the agent push, with targeted denies on force/delete/mirror/`+refspec` | Agent-side deny rules are text patterns and leaky by construction; a server-side rule cannot be bypassed by flag placement. `enforce_admins` because the maintainer account is an admin and admins otherwise bypass protection. No required reviews or checks, so direct pushes keep working | owner decision |
| 2026-10-27 | The local test environment's Triton tracks the pin in `toolchain.Dockerfile` | After the bump, the default test env still pointed at the v3.7.1 tree, so a green suite would have validated the wrong Triton | session, close-out |
| 2026-10-27 | Keep jq as a build prerequisite rather than reading the LLVM pin with `python3` | Our build of Triton's LLVM should mirror Triton's own build as closely as possible, and Triton's `build-llvm-project.sh` reads the pin with jq. Python would drop a dependency but diverge from upstream; the post-build HEAD-vs-pin check already makes a bad read loud either way. Upstream: commented on triton-lang/triton#12413 asking for `set -e` + jq as a documented prerequisite | owner, session |
